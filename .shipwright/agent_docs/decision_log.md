# Decision Log — nidea-invoice

### ADR-001: Adopt this repository into the Shipwright SDLC

- **Status**: accepted
- **Date**: 2026-10-20
- **Commit**: `49c0ddaa837e1a13c067188022b8db4f627aa448`

#### Context

This repository existed with 10 detected feature(s) and substantive git history before /shipwright-adopt ran. The goal is to bring it under the Shipwright SDLC (CLAUDE.md + .shipwright/agent_docs + .shipwright/planning/ + .shipwright/compliance/ + configs) without disrupting the existing codebase.

#### Decision

Adopted into Shipwright using profile `generic` and scope `full_app`. Retroactively seeded `phase_tasks[]` for `["project", "plan", "build", "test"]` (marked `establishedAtAdoption`) so that `/shipwright-iterate` and downstream skills (`/shipwright-compliance`, `/shipwright-test`) work as on a natively-built project.

#### Consequences

- Future changes MUST go through `/shipwright-iterate` (not `/shipwright-project`/`/shipwright-plan`/`/shipwright-build`).
- Compliance reports (RTM, SBOM, change-history) are seeded; test-evidence starts collecting from the first `/shipwright-test` run.
- Any existing E2E baseline auto-generated by Adopt (under `e2e/flows/adopted-baseline.spec.ts`) is a regression guard, not a substitute for real acceptance tests.

#### Rejected alternatives

- Manual `/shipwright-project` init: would lose git history and force re-description of existing code.
- No adoption (ad-hoc `/shipwright-iterate`): would mean missing configs, no compliance reports, and the audit pipeline would silently no-op.

### ADR-002: refactor: share PDF blob helper, split bundle, enable strict TypeScript

- **Status**: accepted (retroactive, llm-inferred)
- **Commit**: `7ac7ddc03da91f596cdb9bc61323572d3ce16e2f`

#### Context
The initial JavaScript bundle was about 900 kB, above Vite's 500 kB chunk warning, because jsPDF, the secondary pages and all vendor code shipped in one chunk. Base64-to-Blob conversion for print and save was duplicated, and TypeScript ran in non-strict mode, hiding type errors.

#### Decision
Load jsPDF and the Settings and Info pages on demand, split react/react-dom/react-router-dom and supabase-js into their own long-lived vendor chunks, extract a shared dataUriToBlob helper, and enable TypeScript strict mode.

#### Consequences
Initial JS dropped to about 520 kB with no chunk over 500 kB, and vendor chunks cache across deploys. The first PDF generation and the first visit to Settings or Info incur an extra network fetch. New code must type-check under strict mode, which `npm run build` enforces in CI.

### ADR-004: Static site on Bunny CDN with an edge-rule route to the lookup service and a Shield per-IP limit
- **Date:** 2026-10-21
- **Section:** Iterate — change: host the app on Bunny at wartgeld.nidea.ch
- **Run-ID:** iterate-2026-10-21-bunny-static-hosting
- **Context:** Step 3 of the hosting migration: the app ran on Netlify while the Swiss Post lookup service already ran on Bunny Edge Scripting. The user wanted the app on nidea.ch, a per-visitor request limit, e2e tests in CI and a budget under 2 EUR/month.
- **Decision:** Serve the built site from a Bunny storage zone + pull zone at wartgeld.nidea.ch; an exact-URL edge rule forwards /api/address to the lookup service with a secret marker header; Bunny Shield (free) limits 50 lookups/10 s per IP on the site zone and on direct calls to the service (marker exempt). Settings move via a file export/import. Publishing is a manual npm run deploy:site.
- **Commit:** (assigned post-merge)
- **Rationale:** The deciding reason was a real per-IP limit: the edge script counts per instance, so only Shield gives a per-visitor limit, and it is free. Edge-rule origin switch was probed live and works on a storage pull zone.
- **Consequences:** One web address and one bill; per-IP limiting at the edge. The limit is per IP, not per person (IPv6 rotation accepted, service cap is the backstop). Bunny resources are hand-configured and documented in docs/bunny-hosting.md. Netlify stays as a fallback until a follow-up forwards it.
- **Rejected:** Serving the static files from the edge script (credentials next to the bundle, every page view a script run, no immutable CDN assets); Netlify rate limiting (paid plan); keeping Netlify as the main host.

### ADR-006: Print on iPhone and iPad through the system share menu
- **Date:** 2026-10-22
- **Section:** Iterate — bug: iPhone print blank page
- **Run-ID:** iterate-2026-10-22-ios-print-blank
- **Context:** On iPhone Safari «Drucken» printed an empty page: printPdf loaded the PDF into a hidden (display:none) iframe and printed it, and iOS/iPadOS Safari never draws a PDF inside such a frame. Desktop browsers do, so tests stayed green.
- **Decision:** On iOS/iPadOS (iPhone/iPad/iPod UA, or Macintosh with touch) «Drucken» calls navigator.share with the PDF file inside the tap; the share menu offers «Drucken». Cancel or a second tap does nothing; no file sharing or a failed share opens the PDF in a new tab; if Safari blocks that tab, a toast suggests «Speichern». Computers keep the hidden-frame print.
- **Commit:** (assigned post-merge)
- **Rationale:** User chose the share menu over opening the PDF in a new tab (stays in the app, one step to the printer). Fixes the root cause (iOS never reaches the hidden-frame path) rather than retrying the frame.
- **Consequences:** Printing on iPhone takes one extra step (share menu → Drucken) but works. Real-device behaviour is verified by the user after deploy, not by automated tests. In-app browsers without file sharing may show a blank fallback tab (accepted).
- **Rejected:** Opening the PDF in a new tab as the main path (user preferred the share menu); rendering the PDF to images for printing (heavy, new dependency); a visible iframe (iOS still prints only the page, not the PDF).

### ADR-007: Redesign the invoice page with a live preview on desktop and a bottom sheet on phones

- **Run-ID:** iterate-2026-10-22-redesign-invoice-page

### ADR-009: Redesign Settings and Info, add a setup status and a German theme menu that follows the system
- **Date:** 2026-10-22
- **Section:** Iterate — change: settings and information pages, theme menu, setup status (redesign part 3)
- **Run-ID:** iterate-2026-10-22-redesign-settings-info
- **Context:** Part 3 of the Papier & Tanne redesign. Settings fields showed the example sender and 'Kanton Zug' as if saved, and a partial save wrote those defaults into storage, so the app could not tell what the midwife had really entered. The theme menu was English, 'System' did not follow OS changes while open, dark users saw a light flash, the page was not marked German and menu focus was nearly invisible.

Multi-tab edits can still overwrite each other (unchanged).

### ADR-018: Place the invoice recipient block for a C5 right-window envelope
- **Date:** 2026-10-31
- **Section:** Iterate — bug: invoice address fits the envelope window
- **Run-ID:** iterate-2026-10-31-envelope-window-address
- **Context:** A printed invoice to Stadtverwaltung Zug, folded in half in a C5 right-window envelope, hid the postcode/town line below the window: the recipient block sat at baselines 65-80 mm and the sheet slides ~13 mm inside the envelope.
- **Decision:** Move the recipient block up 11 mm to baselines 54/59/64/69 mm (x=120 mm, 5 mm pitch), printing non-empty lines consecutively. Tests read real line positions from the PDF and require the 48-72 mm window band.
- **Commit:** (assigned post-merge)
- **Rationale:** Measured on the user's envelope: window ~53 mm from the top, ~45 mm tall; text appeared ~20 mm lower than its PDF position. 54-69 mm centres the block in the band visible at every slide position.
- **Consequences:** All four recipient lines stay visible across the sheet's play in the envelope; the gap to the invoice title grows. Real-envelope fit still needs one physical test print.
- **Rejected:** Moving it 15 mm (start 50 mm) risked clipping the first line when the sheet sits at the top of the envelope; changing recipient data (splitting 'Postfach') was out of scope.
